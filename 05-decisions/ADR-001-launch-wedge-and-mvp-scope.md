# ADR-001: 首发切入与 MVP 范围

> **修订（2026-08-17）：** 人群收窄、P0 边界与安全规则继续有效；"验证闸门"（8-12 人原型测试后再进生产开发）由 [ADR-002](ADR-002-defer-formal-user-testing.md) 取代——正式测试推迟至 v0.3 前，v0.2 以创始人自用验证。

## 决定

PATH 的长期产品覆盖“开始、重返、建立规律、进阶、扩展能力”的连续路径；但 **v1 验证与首个生产切片只服务于有基础训练场地、正在重返或已开始每周 1-3 次训练的人**。

该人群不要求会自主编程或已经有稳定训练习惯，但应能在家中或基础商业健身房完成经确认的基础动作，或愿意选择低门槛替代动作。v1 不承诺动作教学、动作质量判断、疾病/伤病处理或高阶专项编程。

这是一个验证期的工作决定，不是永久市场排他。零基础“第一天开始”入口会保留在状态模型中，但不作为首发主场景。

## 要解决的工作

目标用户在以下时刻需要帮助：

> 在今天真实的时间、场地、精力和限制下，选择一节安全可完成的训练；完成或调整后，理解这次记录支持什么、不支持什么，并决定下一步如何继续。

成功不是让用户打开更多课程或记录更多数字，而是让用户能回答：

1. 当前 4-6 周最重要的训练方向是什么。
2. 今天为什么推荐这一版本，而不是另一版本。
3. 发生变化时我可以怎样改，系统会如何记住。
4. 当前证据支持什么，哪些事情仍不能下结论。

## 证据与推理

### 已确认的输入

- 调研显示，课程、训练日志、自动排课、饮食记录、穿戴数据和运动社区均已有成熟玩家；这些能力任一单独做强都不足以构成 PATH 的差异。详见 [市场与公开反馈调研](../MARKET_AND_USER_RESEARCH_V0_1.md)。
- Fitbod、Freeletics 等证明动态计划有需求；公开讨论也显示，黑箱推荐、动作不连贯与不适场景会损害用户信任。该类信号只能说明风险与假设，不能量化发生率。
- Strong、Hevy、训记的用户重视低摩擦、可自定义的真实记录；公开反馈同时显示，器械占用时需要替代动作，数据本身也不足以说明是否进步。
- 对饮食记录，公开讨论与已有一手经历均显示其价值和成本并存。精确热量记录不宜成为开始训练的门槛。
- 现有原型已经覆盖重返、建立规律、自主进阶三条可点击路径，并已实现安全分流、训练调整与证据复盘。

### 本次推理

- 零基础用户会放大动作教学、风险、内容供给和信任成本；高阶训练者会放大周期化与专项自由度。二者同时首发会掩盖 PATH 要验证的核心闭环。
- 重返 / 建立规律 / 初步自主训练者共同面对“现实不匹配、缺少判断、看不懂进步”，且可以用同一套 `CurrentState -> Mission -> Program -> Session -> Evidence -> Review -> Decision` 验证。

上述是产品假设，需通过用户测试与真实使用数据修正。

## P0 能力边界

| 能力 | v1 必须做到 | 明确边界 |
|---|---|---|
| 当前状态 | 用最少输入获得可用时间、场地/器械、准备度、不适与近期节奏 | 不要求体重、照片、食物克数或穿戴设备 |
| 风险分流 | 对急性或持续加重不适压制高强度建议，显示非诊断性支持路径 | 不诊断原因、不推荐“忍一下完成” |
| Mission | 形成一个 4-6 周优先方向，显示成功证据和非唯一裁判指标 | 不能把体重、连续天数或热量变成总分 |
| Program | 为一个训练方向提供完整、短版、恢复/暂停版本及替换动作 | 版本是可选方案，不是顺从等级 |
| Session | 快速记录实际组数、重量/次数、RPE、调整和可选不适 | 不以完整记录为完成前提 |
| Review | 明确呈现事实、有限观察、待确认与候选路线 | 不把单次表现或体重趋势宣称为身体改变原因 |
| Decision | 用户可接受、修改、拒绝或延后下一步；系统保存理由与后续验证点 | 未确认前不得自动加重量、改核心动作或延长 Mission |
| Re-entry | 中断后保留历史，从今天重新确认状态 | 不显示断练天数、补债或惩罚 |

## 延后项

以下内容可存在于长期路线，但不进入 v1 功能承诺或首轮生产范围：

- 通用聊天式 AI 教练、动作识别、相机纠错、伤病/疼痛诊断。
- 大型课程库、商城、教练交易、社交信息流、排行榜和赛事系统。
- 精确饮食记录、卡路里目标、体型前后对比和自动化身体变化归因。
- 自建硬件平台、复杂可穿戴评分、完整营养/睡眠/冥想中台。
- 高阶周期化、专项运动编程、多用户协作和教练端。

## 体验原则

1. **先给下一步，再给数据。** 用户打开产品时首先应知道“今天可以怎么做”。
2. **先陈述事实，再给观察。** 推荐必须可回溯；不确定性必须可见。
3. **短版、恢复和暂停是主路。** 它们不应隐藏在失败页、二级菜单或提醒之后。
4. **游戏感服务于理解。** Mission、路线和阶段现场记录表达积累，不表达胜负、比较或自我惩罚。
5. **用户拥有最后决定权。** 系统可以建议，但每次影响计划的改变都需要可见的用户选择。

## 验证闸门

在进入生产开发前，对 8-12 名参与者完成 [v1 原型验证](../V1_PROTOTYPE_VALIDATION.md)，并用以下门槛判断是否继续：

| 问题 | 通过信号 | 失败信号 | 后续动作 |
|---|---|---|---|
| Mission 是否可理解 | 多数参与者不看提示能复述当前优先方向与非唯一裁判 | 将 Mission 误读为体重目标、课程标题或等级 | 改写 Mission 构成与入口 |
| 推荐是否可解释 | 多数参与者能指出至少两条输入事实，并能找到替代选项 | 认为系统随机、强制或“AI 说了算” | 重做理由、证据和拒绝入口 |
| 调整是否体面 | 用户主动选择短版/替换/暂停时不感到失败，理解记录会被保留 | 选择短版后认为被扣分或计划已废 | 调整文案、反馈和后续复盘 |
| 复盘是否诚实 | 用户能区分事实、观察、待确认，不把稳定表现误读成体型保证 | 用户把任何图表/海报当成身体改变结论 | 降低视觉宣告性、强化边界 |
| 安全边界是否清楚 | 风险情境下用户预期系统停止高强度建议，而非诊断 | 用户误以为产品在评估或批准其身体状态 | 修改筛查、提示和路由 |

若关键理解任务无法通过，不进入更多训练内容或视觉扩张；先修复核心决策闭环。

## 交付顺序

1. **研究准备：** 用现有筛选条件招募 8-12 人，执行任务式原型测试，逐条记录失败点。
2. **范围复盘：** 依据测试把 P0 缩减至能支持闭环的最小数据、规则和页面；冻结一条主场景与一条重返场景。
3. **生产垂切：** 实现匿名/账户、状态采集、规则服务、训练记录、复盘与用户确认的最小真实数据链路。
4. **封闭试用：** 让小规模用户真实使用 2-4 周，观察回归、调整和理解，而非只看打卡量。
5. **再决策：** 用真实数据决定是否扩展零基础动作教学、饮食、穿戴接入或教练协作。

## 影响

- 现有 `V1_PRODUCT_CONTRACT.md` 的核心对象与安全规则继续有效。
- 现有交互原型可继续用作测试材料，但不是生产需求的全部。
- 产品、设计和工程后续新增能力必须说明：它服务 P0 的哪一步、使用何种证据、被拒绝或失败时如何降级、是否触碰健康安全边界。
